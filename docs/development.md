# Development

- `cargo xtask views` regenerates `docs/views/`: the crate graph and the `stream` and `desk` state machines, produced by running core's `decide` and `evolve`. Never edit those files by hand.
- `cargo xtask check` runs the gates CI runs: `phonepad-core` has no dependencies, no comments in Rust, JavaScript or `pad.html`, the page tests (every tracked `*.test.js`, run with `node --test`; it fails when none is tracked or Node is missing) pass, and `docs/views/` matches the code.
- `target/debug/xtask profile <pid> <seconds>` writes a perf hot-path summary to `docs/views/hot-path.md`. Run it directly, not through `cargo`, if your cargo runner isolates PIDs. It needs a live Hyprland session, so CI never runs it.
- `cargo xtask e2e [--bin <phonepad>]` builds phonepad (or takes `--bin`), runs a test instance on port 8769 as `test@example.invalid` with its own runtime dir `$XDG_RUNTIME_DIR/ppe2e` and a stub `owe` first on `PATH`, and prints one PASS/FAIL line per check: the Hyprland and Wayland sockets connect through that dir, a wrong or missing login gets 403, one and then three viewers each receive units whose first is a keyframe and which ffmpeg decodes frame for frame, the instance survives the sessions, and SIGTERM sent while a fourth viewer is streaming ends it with code 0 within 5 s. A still desktop is enough: each viewer that joins requests a keyframe, which is encoded from the held frame without damage. The viewers send only `view`, `visible` and `ack`, never input, so the pointer and the desktop stay untouched. It needs a live Hyprland session, the iGPU, `/dev/uinput` and the ffmpeg CLI, so CI never runs it.
- `cargo xtask latency [--bin <phonepad>] [viewer | touch] [port=<port>] [seconds=<s>] <profile>...` runs a test instance on port 8771 (or `port=`; another port gets the runtime dir `pplat<port>`, so two runs can share the desktop) as `test@example.invalid` (runtime dir `$XDG_RUNTIME_DIR/pplat`, stub `owe`, `PHONEPAD_TIMINGS` set) behind a userspace network emulator, circles the real pointer with its own uinput mouse (6 px every 8.3 ms, a 229 px radius), and opens the real page in headless Chromium through the emulator (412×915 CSS px at scale 2.625, the login header added over DevTools, software decoding; `PHONEPAD_CHROMIUM` names the browser). Each profile is one phase on the same instance and page: 3 s to settle, then 15 s measured (or `seconds=`). With `viewer`, the client is the acking viewer of the known case instead of the page: it acks each unit on receipt and reports it drawn at the same instant on its own clock, so stalls are gaps in arrival and send→ack carries no decoder. It prints one row per profile: units/s and Mbit/s of acked units, drawn units/s, stalls (gaps over 250 ms between drawn units, on the page's clock) with the longest gap, and p50 / p95 / max in ms of capture→send, send→ack, capture→ack, receive→decode and decode→draw. Profiles: `lan` (nothing added), `wifi` (10 ms, 50 Mbit/s), `lte` (60 ms ±20 ms, 10 Mbit/s), `bad-lte` (150 ms ±50 ms, 3 Mbit/s, 1% loss), or `rtt=<ms>,jitter=<ms>,rate=<Mbit/s>,loss=<%>`. It needs a live Hyprland session, the iGPU, `/dev/uinput` and Chromium, so CI never runs it.
  - The emulator, per TCP connection and direction: it reads at most one 1448-byte segment at a time and queues at most 64; a full queue stops reading, so the sender's socket backs up as behind a real bottleneck. A segment starts onto the link when it arrives or when the one before it has left, whichever is later, and takes its bits at the cap. It then travels half the round trip plus a uniform jitter of ± half the jitter figure, so a round trip varies by ± the jitter figure, and never arrives before the segment ahead of it, since TCP delivers in order. A lost segment (each segment in each direction, with the loss probability) arrives one retransmission later, max(200 ms, 2 × RTT): Linux's minimum retransmission timeout, or its tail-loss probe after two round trips. Everything behind it waits, as head-of-line blocking does. Profile delays are round trips split evenly between the directions, and the cap applies to each direction.
  - `cargo xtask latency calibrate` is the known case for the emulator and the timing records: a viewer that acks each frame on receipt (no decoder) at added RTT 0, 100 and 200 ms and at a 2 Mbit/s cap. It passes when send→ack p50 rises by 100 and 200 ms ± 15 ms, the stream stays at or under 2.1 Mbit/s, and a 750 KB bulk transfer through the 2 Mbit/s cap measures 1.9–2.1 Mbit/s at the receiver. The stream alone carries far less than 2 Mbit/s, so only the bulk transfer shows the cap binding. The page is not the known case: its software decoder adds 5–90 ms to send→ack, varying with the screen content, so its send→ack has no known answer.
  - `nested` runs against a Hyprland of its own (`hyprland=<binary>`, default `/usr/bin/Hyprland`), a window on the live session's active workspace with its own signature and socket and the host pointer disabled, so units/s is no longer bounded by how often the live screen changes. Its pointer is parked at the centre and its only client repaints a band through the centre with the next of 8 grey levels `hz=` times a second (default 60). With `viewer`, ffmpeg decodes what the viewer received at one point of the band, and a second table gives per phase repaints/s, changes/s seen (acked units whose level differs from the unit before) and units/s; units/s exceeds changes seen when content is encoded twice. `touch` is refused with `nested`: its moves reach phonepad's uinput devices, which only the live Hyprland reads.
  - `cargo xtask latency nested calibrate` is its known case: lan at 0, 20 and 125 Hz, each passing when changes seen per second are within 10% of min(repaints/s, the nested refresh rate).
  - With `touch`, nothing circles the pointer with uinput: the harness touches the page instead, one finger circling the pad's centre at a 60 CSS px radius in 120 `Input.dispatchTouchEvent` moves a turn (each call returns once the page took it, about one per display frame), one gesture per phase, so the page's own moves drive the test instance's pointer. The page reports to a `globalThis.padProbe` the harness defines before it loads: for each redraw after a touch, the touch event's timestamp, when its handler ran and when the ring was drawn, and for each pointer message the predicted pointer before and after it and the direction of the last sent move. Per profile it checks touch→ring-redraw (handler to draw, `performance.now()`) p95 ≤ 20 ms and the largest backward jump at a reconciliation (the jump's component against the last move, or its whole length with no move) ≤ 4 px, and prints the event-timestamp→draw spread and the largest jump in any direction. Known cases, run on this desktop: a page that busy-waits 30 ms per paint fails the redraw check (p95 30.6 ms), and a page that forgets its in-flight moves at each pointer message fails the jump check on lte (7.8 px). The draw time is when the page drew the canvas, not when the pixels reached the screen; headless Chromium's input pipeline adds about two frames before the handler runs (event timestamp→draw p50 33 ms), which no page change can remove.
  - Limits: the page decodes in software (headless Chromium's VA-API decoder fails here), which the phone does not, so receive→decode and send→ack are larger than on a phone and slow acks hold flow-control credit longer; the stream is whatever the live screen shows, so units/s and bytes change between runs.
- CI (`.github/workflows/ci.yml`) runs fmt, clippy with `-D warnings`, the tests and `cargo xtask check`.
